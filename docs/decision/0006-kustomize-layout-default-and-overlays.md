# Lay out deploy manifests as a default kustomize root plus per-mode overlays

## Context and problem statement

Squirrel supports two cert-source modes (self-signed and cert-manager) and emits CRDs, RBAC, and a MutatingWebhookConfiguration through `controller-gen`.
Operators need a one-command install path for either mode, and the install must compose the controller-gen output with hand-written manifests (Namespace, ServiceAccount, Deployment, Service, ClusterRoleBinding) and with the per-mode patches the design requires (MWC namespaceSelector, cert-manager annotation).
The project needs a single, conventional layout under `config/` that supports both modes without duplicating manifests or hiding the controller-gen output behind a build step.

## Decision drivers

- The default install must be a single `kubectl apply -k <path>` per cert mode.
  Operators should not need a kustomize binary on top of `kubectl`.
- The two modes must share as much manifest as possible.
  Duplicating the Deployment, Service, RBAC binding, and MWC patches across two trees would drift over time.
- The controller-gen output (CRDs, ClusterRole, MWC) must be tracked in git so reviewers can see the diff when a marker changes, and so CI can fail on drift via a regenerate-and-`git diff` check.
- The design specifies a `namespaceSelector` on the MWC that controller-tools' webhook marker cannot express; the layout must give that selector a clear, reviewable home rather than hiding it as a runtime patch.
- Future maintainers must be able to find each piece by directory name without reading a README first.

## Considered options

- Default kustomize root at `config/default`, with `config/overlays/cert-manager` layered on top.
- One kustomize root per mode (`config/self-signed`, `config/cert-manager`), each pulling shared resources from `config/manager`, `config/rbac`, etc.
- A single kustomize root with the cert-manager-mode bits gated behind kustomize components.
- Pre-rendered YAML per mode, no kustomize involved.

## Decision outcome

Chosen option: "default kustomize root plus a cert-manager overlay layered on top of it".
This is the kubebuilder-shaped layout most Go operators in the Kubernetes ecosystem use; future contributors familiar with `make manifests` will recognise it immediately.
The shared resources live one level up (`config/manager`, `config/rbac`, `config/crd`, `config/webhook`) and both roots compose them via the standard kustomize `resources:` list.

### Layout

```text
config/
├── crd/
│   ├── bases/                                 # controller-gen output (tracked)
│   └── kustomization.yaml
├── rbac/
│   ├── role.yaml                              # controller-gen output (tracked)
│   ├── role_binding.yaml                      # hand-written
│   └── kustomization.yaml
├── webhook/
│   ├── manifests.yaml                         # controller-gen output (tracked)
│   └── kustomization.yaml
├── manager/
│   ├── namespace.yaml
│   ├── service_account.yaml
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
├── default/                                   # self-signed mode root
│   ├── kustomization.yaml
│   └── mwc_patch.yaml
└── overlays/
    └── cert-manager/                          # cert-manager mode overlay
        ├── kustomization.yaml
        ├── certificate.yaml
        ├── deployment_patch.yaml
        ├── mwc_patch.yaml
        └── role_patch.yaml
```

`config/default` is the self-signed mode and the documented install path.
`config/overlays/cert-manager` layers on top of `config/default` rather than reproducing its content; the `resources: [../../default, ...]` reference threads every default-overlay patch (namespaceSelector, MWC rename, RBAC binding) through to the cert-manager install with no duplication.

### Per-mode responsibilities

- **`config/default`** applies the patches that turn the controller-gen-emitted MWC into a real one: rename the resource to `squirrel-image-rewrite`, point `clientConfig.service` at the real Service, and add the design's `namespaceSelector` (opt-in label + system-namespace exclusion).
- **`config/overlays/cert-manager`** adds the `cert-manager.io/inject-ca-from` annotation on the MWC, replaces the Deployment's emptyDir cert volume with a Secret projection cert-manager owns, swaps `--cert-source=cert-manager` into the manager args, and trims the RBAC verbs the cert-manager mode does not need (`secrets`, `mutatingwebhookconfigurations`).

### Generated vs hand-written

- Generated by `make manifests` (committed): `config/crd/bases/*.yaml`, `config/rbac/role.yaml`, `config/webhook/manifests.yaml`.
  The `make verify-manifests` target re-runs the generator and fails on `git diff`, so a CI check catches a contributor who edited a marker without regenerating.
- Hand-written: the per-directory `kustomization.yaml` files, every file under `config/manager`, `config/default`, and `config/overlays/cert-manager`, plus `config/rbac/role_binding.yaml`.

### Consequences

- Operators get a one-command install for each mode (`kubectl apply -k config/default` or `kubectl apply -k config/overlays/cert-manager`).
- The shared resources (Deployment, Service, ClusterRoleBinding) live in exactly one place; a security fix to the Deployment's `securityContext` lands once and both modes pick it up.
- The `namespaceSelector` the controller-gen marker cannot express has a single, reviewable home (`config/default/mwc_patch.yaml`).
- Reviewers see the controller-gen diff when a marker changes, because the output is tracked.
- Contributors who already know kubebuilder's layout find every file where they expect it.
- The cost is one extra directory level (`config/overlays/`) on the cert-manager mode compared with a flat `config/cert-manager` peer of `config/default`; this trades a longer install path for an unambiguous "this is an overlay on top of the default" signal.

## Confirmation

- Both apply paths produce the same set of cluster-scoped resources (CRDs, ClusterRole, ClusterRoleBinding, MWC) and the same namespace-scoped resources (Namespace, ServiceAccount, Deployment, Service); the cert-manager overlay additionally produces an `Issuer` and a `Certificate`.
- `kubectl apply -k config/default` and `kubectl apply -k config/overlays/cert-manager` are both single-command installs that leave the cluster in a working state.
- The `make verify-manifests` target catches marker drift before review.
- The `INSTALL.md` walkthrough does not need to mention the layout; the directory names are self-explanatory.

## Pros and cons of the options

### Default kustomize root plus a cert-manager overlay

- **Good**, because operators run the same shape of command for both modes (`kubectl apply -k <path>`).
- **Good**, because the cert-manager overlay layers on top of `config/default` and inherits every patch the default applies; a fix to the namespaceSelector or to a `securityContext` field lands once.
- **Good**, because the layout matches kubebuilder's convention; contributors familiar with the ecosystem find files where they expect.
- **Bad**, because the cert-manager mode lives under `config/overlays/` rather than as a peer of `config/default`, so the install path is slightly longer.

### Two peer roots (`config/self-signed`, `config/cert-manager`)

- **Good**, because both install paths have the same shape (`kubectl apply -k config/<mode>`).
- **Bad**, because shared patches (the namespaceSelector, the Deployment securityContext) would need to be expressed twice or pulled into a common kustomize Component, adding indirection.
- **Bad**, because the "cert-manager mode is the default plus a few overrides" relationship is hidden by the symmetric layout, so reviewers cannot see what the cert-manager mode actually changes.

### Single root with kustomize Components

- **Good**, because every shared resource lives in exactly one place.
- **Bad**, because Components are a less-familiar kustomize feature; many contributors have not used them.
- **Bad**, because `kubectl`'s embedded kustomize did not fully support Components until relatively recently; the K8s 1.33 target supports them but documenting "use the right kustomize binary" adds friction.

### Pre-rendered YAML per mode

- **Good**, because operators do not need any kustomize knowledge.
- **Bad**, because every change has to be made twice and the two files drift over time.
- **Bad**, because reviewing a PR that touches both files requires reading both diffs against the source of truth elsewhere.

## More information

The kustomize layout is exercised by the `INSTALL.md` walkthrough and the worked examples in `USAGE.md`.
Future modes (e.g. external secret-store-driven certs) would follow the same shape: a new overlay under `config/overlays/`, layered on top of `config/default`.
